# GateHeal Security & Threat Model (status after WP8)

## 1. Trust Boundaries
GateHeal enforces four explicit trust zones:
1. **Zone 1 (Isolated Linux Lab):** Disposable QEMU/KVM Ubuntu VM verified via `/etc/gateheal-lab-sentinel` and `systemd-detect-virt`.
2. **Zone 2 (Observation & Sanitization):** `IncidentCollector` performs best-effort full-text secret redaction before line splitting, enforces per-line byte caps (`512` B) and per-service fair byte budgets, keeps the newest tail lines, and wraps every log line in `[UNTRUSTED_LOG] `.
3. **Zone 3 (Advisory Plane):** Deterministic `DiagnosisEngine` and bounded `AgentProposer` modules. Possesses zero subprocess execution authority. From WP7 the advisory module can be a hosted language model (section 4).
4. **Zone 4 (Independent Policy, Execution & Oracle Plane):** `PolicyEngine` (sole minting authority for single-use HMAC-signed `AuthorizedActionCapability` objects), `MinimalImpactSelector`, `ExecutionController`, `OutcomeVerifier` (independent multi-sample soak oracle), `EscalationSink`, and `AuditRecorder`.

## 2. Host Workstation Protection & Guest Sudoers Contract
- `LocalLabSubprocessTransport` requires `GATEHEAL_INSIDE_LAB=1`, a non-`omarchy` kernel, `/etc/gateheal-lab-sentinel` matching `GATEHEAL_ISOLATED_LAB_GUEST_V1`, and `systemd-detect-virt` reporting an allowed guest hypervisor/container.
- `SSHLabTransport` enforces a loopback target IP (`127.0.0.1`/`::1`/`localhost`), validates `--ssh-user` against `^[a-z_][a-z0-9_-]{0,31}$`, uses a dedicated `UserKnownHostsFile` (`~/.cache/gateheal-vm/known_hosts`) with `IdentitiesOnly=yes`, places `--` before `user@host`, verifies `/etc/gateheal-lab-sentinel` over SSH by default (`verify_remote_sentinel=True`), distinguishes SSH connectivity failures (`TransportUnavailableError` on exit `255`/`124`/`137` or timeout) from missing/mismatched sentinel files (`HostSafetyViolationError`), and supports remote `timeout` + `/usr/bin/systemd-run --scope`.
- Mutating service actions execute via `sudo -n /usr/bin/systemctl reload|restart <unit>`, matching the `visudo -cf` verified allowlist in `lab/systemd/gateheal-sudoers.conf`.
- **Dual-Key Controller vs. Harness SSH Separation (Spec H):** The controller uses an unprivileged SSH key (`id_ed25519`) authorized solely for `ubuntu` (and explicitly rejected for `root` with exit `255` `Permission denied`), whereas fault injection and lab resets use a separate harness key (`id_harness_ed25519`) installed exclusively in `/root/.ssh/authorized_keys` (without `from="127.0.0.1"`, because QEMU SLIRP user-mode port forwarding presents the host connection source as `10.0.2.2` inside the guest). QEMU user networking runs with `restrict=on` (Spec C4) so the guest cannot initiate outbound network connections.

## 3. Verified Mitigations vs. Known Limitations
- **Verified in Automated Test Suite (`SIMULATED` & `LIVE_QEMU_KVM_GUEST`):**
  - Closed `ActionId` enum lookup, strict unit regex (`^[a-z0-9_-]+\.service$`), inventory allowlisting, and `shell=False` argument vectors.
  - Capability-bound `ExecutionController.execute()` with mandatory `expires_at_utc`, execution-time `PolicyEngine.evaluate()` re-verification, proposal/decision digest, and TOCTOU state-hash checks.
  - Per-incident retry budgets (`incidents[incident_id]`) separated from persistent per-unit cooldowns and flap counters keyed by the mutated unit (`units[target_unit]`).
  - Independent multi-sample `OutcomeVerifier` soak polling (`verification_soak_sec` / `verification_poll_interval_sec`) detecting crash recurrence via `NRestarts`, `InvocationID`, `ExecMainStartTimestampMonotonic`, and `active -> failed -> active` state transitions; read-only diagnostic actions, `no_op`, and `abstain_and_escalate` skip the soak window (`samples_collected=1`).
  - Bounded `communicate(timeout=...)` and pipe closure after `os.killpg` so orphan grandchildren holding stdout/stderr pipes in a new session cannot hang the controller.
  - Write-ahead (`"intent"` and `"completed"`) SHA-256 hash-chained audit logs with `.anchor` checkpoint persistence across log rotation.
  - **Empirical systemd Conformance & Sudoers Negative Isolation (WP5):** Verified that `Restart=no` leaves `NRestarts=0` on `SIGKILL`, `InvocationID` and `ExecMainStartTimestampMonotonic` remain identical on `reload` and change on `restart`, `SIGKILL` yields `ActiveState=failed` and `Result=signal`, active restart terminates coupled workers while start-failed preserves them, unprivileged `ubuntu` reads unit properties and journals cleanly (`FACT_6`), `ExecStartPre` validation failures prevent service startup while preserving downstream workers (`FACT_7`), and all argument-injection / unapproved sudo subcommands fail with explicit sudo denial messages (`check_conformance.sh`).
- **Known Limitations:**
  - **Best-Effort Log Redaction:** Regex-based secret redaction (`redact_secrets_text`) scrubs known credential formats (complete and head/tail-truncated PEM blocks, JWTs, GitHub PATs, AWS keys/secrets, Stripe/Slack tokens, Basic/Bearer headers, cookies, and URL credentials), but cannot guarantee redaction of arbitrary custom or unformatted secrets.
  - **Unkeyed Audit Hash Chain:** Without an external HMAC key (`GATEHEAL_AUDIT_HMAC_KEY`) stored outside the controller's writable directory, SHA-256 hash chaining is tamper-evident only against accidental corruption or truncation; a local attacker with write access to the log files can recompute unkeyed hashes.
  - **Single-Process Prototype Key Storage:** In this prototype, the capability secret and `GATEHEAL_APPROVAL_HMAC_KEY` reside in the same OS process memory space as the controller.
  - **Active-Session Coupling vs. `systemd` `PartOf=` / `BindsTo=` Coupling Limitation:** GateHeal's blast-radius model assumes starting a non-active (`failed`/`inactive`) unit has `B_dep = 0.0` because no live process on the target is terminated. If a downstream unit uses `PartOf=` or `BindsTo=` in `systemd`, restarting a `failed` upstream unit can still trigger `systemd` to stop/restart the downstream unit unless that systemd-level propagation is encoded in the inventory. Therefore, `lab/systemd/lab-worker.service` uses `Wants=lab-api.service` rather than `BindsTo=` or `PartOf=`, and in the lab daemons (`lab_daemons.py`), `lab-api`'s `SIGTERM` handler notifies `lab-worker` when an active `lab-api` is hard-restarted (breaking `lab-worker` on an active restart in `S5`/`S5B`/`S2` while preserving `lab-worker` on `SIGHUP` reload or `S1` `SIGKILL` crash recovery).
  - **Real-Lab VM Execution:** Full end-to-end execution against a live QEMU/KVM guest (`--transport ssh`) requires a booted guest image with `lab/systemd/gateheal-sudoers.conf` installed at `/etc/sudoers.d/gateheal-lab`.
  - **Cross-Incident Restart Bounds:** Because `prior_recovery_attempts` and `action_history` are scoped per `incident_id` (R4), repeated mutating actions across distinct `incident_id`s are bounded **only** by the per-unit `cooldown_sec` and `flap_max_restarts` / `flap_window_sec` limits.
  - **Strict All-Samples-Healthy Soak Rule vs. Slow Startup Grace (D2):** During post-action verification, `OutcomeVerifier` enforces a strict rule requiring **every** soak sample `1..N` (starting at `t1 = verification_poll_interval_sec`) to be healthy (`active`/`running` and probe passing), rather than excusing unhealthy early soak samples under `startup_grace_sec`. This deliberately trades potential false escalations on slow-starting services for fail-safe assurance.
  - **In-Window Soak Unavailability vs. End-to-End MTTR (D3):** `VerificationReport.measured_unavailability_sec` (`in_window_unavailability_sec`) measures only in-window unavailability during the post-action soak window at poll-interval granularity (an upper bound). End-to-end MTTR comes from the experiment harness (`TrialOutcome.service_unavailability_sec`), not from `VerificationReport`.
  - **Manual Restart Resets `NRestarts` & Sub-Interval Crash-Before-First-Sample Gap (D4):** Empirical guest probing (`FACT_5B_MANUAL_RESTART_NRESTARTS` in `check_conformance.sh`, recorded in `nrestarts_manual_restart_observation`) demonstrates that after an automatic `Restart=on-failure` increments `NRestarts=1`, issuing a manual `systemctl restart` resets `NRestarts=0` (`observed=reset`) once the unit stays up past the restart interval (`1.0` s). Furthermore, because `systemctl restart` legitimately replaces `InvocationID` and `ExecMainStartTimestampMonotonic` relative to `pre_incident`, if a restarted service crashes and is respawned *before* the first soak sample (`t < t1`) without leaving `NRestarts > 0`, comparing sample 1 to `pre_incident` cannot distinguish that sub-interval crash from the requested restart; detection relies on `NRestarts` or recurrence across samples `1..N`.
  - **Shared Transport/Mechanism Between Collector and Verifier Oracle (D5):** Although `OutcomeVerifier` maintains a separate code path (`_probe_unit_oracle`) and never calls `IncidentCollector` or `DiagnosisEngine`, both query `systemctl show`, `curl`, and `gateheal.lab_daemons --check-tcp` over the same `CommandTransport`. A stronger application-level oracle can additionally parse and compare the JSON `"boot_id"` / `"reload_count"` fields returned by `GET /healthz`.
  - **Unauthenticated Local Worker Abort Frame in Lab Daemon (D6):** In `gateheal.lab_daemons`, `lab-worker` accepts the `API_HARD_RESTART` termination frame from any local process connecting to `127.0.0.1:8081` without authentication. This is a lab-only fault/collateral simulation hook and not a hardened IPC protocol.
  - **S5 Stale-Pool Fault Is Runtime-Only, Not Persisted (D7):** The first live capture (2026-10-26) showed that persisting `worker_pool_stale: true` in `/etc/lab-api/config.yaml` made the S5B forced restart unrecoverable, because a restart re-reads the config and the API stayed `degraded` (verifier: `not_recovered`). The fault is now injected with `SIGUSR1` (`inject_fault.sh S5_COLLATERAL_TRAP`), which sets an in-memory flag that a restart or `SIGHUP` clears. Consequence for the experiments: S5 models a stale in-memory pool, not a corrupted configuration. A fault that survives restarts is modelled by S2/S4 (invalid configuration), not S5.
  - **Live-Lab Validation Scope and Provenance (D8):** WP5 evidence is one disposable Ubuntu 24.04 QEMU/KVM guest (kernel 6.8.0-147, systemd 255.4) with emulated lab daemons, 3 repeats per scenario (S0-S5B, 21 runs), and the conformance facts FACT_1..FACT_7 plus sudoers and SSH negative checks. It validates the verifier oracle, the policy gate and the coupling behaviour of this lab; it does not establish behaviour on other systemd versions or real services. The manifest records `git_sha`, `git_dirty`, config and sudoers hashes, the base and overlay image hashes, and, when the base image was bootstrapped with the current `manage_vm.sh`, the upstream SHA-256 of the cloud image (`base.upstream.sha256`). A conformance run that is missing any required fact id is never reported as passed (`conformance_is_complete_and_passed`).

## 4. LLM-Assisted Operation (WP6 and WP7)
The language model is an untrusted advisor. It sits in Zone 3, receives a bounded, redacted incident record, and returns proposals; it never executes anything and never mints a capability. The controls below apply to the two LLM arms of the experiment (`B2-LLM` and `G-LLM`, see `docs/experiment-design.md` section 9). Each row of this section is mapped to controls and tests in `docs/threat-test-map.md` (TM-14 to TM-17).

- **Authority of the model.** In `G-LLM` the model's proposals replace the deterministic candidates inside the normal loop, so the `MinimalImpactSelector`, the `PolicyEngine` gate, the single-use capability, the TOCTOU recheck, the `OutcomeVerifier` soak and the audit chain are exactly those of `G`. In `B2-LLM` the model's first proposal is executed ungated by the experiment harness, which only maps `restart_service` and `reload_service` on the three lab units to `systemctl`; anything else runs nothing and is recorded as a harness refusal. That is harness safety for the comparison, not a policy, and it is the reason `B2-LLM` is the ungated control.
- **Untrusted input and hostile output.** Log lines reach the model only after redaction and wrapped in `[UNTRUSTED_LOG] `. The model's answer is parsed as data: invalid JSON, a wrong schema, an unknown action or prose becomes a safe abstention, flagged per call and counted per arm (`Prose answers` in the coverage table). Text inside an answer that looks like an instruction is still just text. An answer cut off by the token limit is a harness limit, not model behaviour: the attempt is invalid and retried.
- **Provider failures are never scored as abstentions.** A timeout, connection error, 5xx or 429 after retries, or a cassette miss makes the attempt invalid and it is retried; a trial that never gets an answer is stored as non-evaluable. Authentication or billing errors (HTTP 401, 402, 403) and the campaign-wide request cap stop the whole run with an explicit exit code instead of producing scores.
- **Planner-excluded clock.** The 45 s incident budget of the controller does not run while the controller waits for the model, so a slow provider cannot make the gate abstain by timeout. The independent oracle still counts model latency as unavailability for both LLM arms, so the cost of a slow model is measured, not hidden. The pre-execution recheck compares the evidence from before the model call with fresh evidence after it; if the lab changed during a long call the action is aborted and escalated (`abort_reason`). Residual risk: a slow model lengthens the outage, but it cannot make the gate fail open.
- **API key handling.** The key is read from an environment variable at run time (default `DEEPSEEK_API_KEY`, overridable with `--llm-api-key-env`). It is never written to any record, cassette or manifest, is redacted from error text, and a missing key stops the run before anything is sent. A key that was ever pasted into a chat, a shell history line, a file or a commit must be treated as exposed and revoked.
- **Cassette.** `llm_cassette.jsonl` is an append-only audit log of every request and raw response, keyed by the SHA-256 of the request. It tolerates a torn last line. It is not a replay of a fresh run, because each request contains the incident id and a collection timestamp.
- **Data leaving the lab.** Incident records (unit states and log excerpts of the lab VM) are sent from the host to a third-party API. The guest itself has no outbound network (`restrict=on`). The lab contains no personal data; a real deployment would need to review what its logs contain before sending them anywhere.
- **Model identity.** The provider is a gateway in front of a reasoning model, so the model behind the name cannot be verified. The thesis reports the model served under that ID on the date of the run. The prompt version (`wp7-3`) and its SHA-256, the model name, the endpoint host and the request budgets are stored in `wp6_manifest.json`.
- **What the results do and do not show.** The experiment shows that the gate removed every harm the ungated model caused (0 of 100 against 3 of 100 trials) and that `G-LLM` always escalated on the unrecoverable scenarios (40 of 40 against 18 of 40). It does not show that the model is safe: the model caused harm in only 3% of ungated trials, so the harm test (H4a) is underpowered, and non-inferiority of clean recovery (H4b) was not shown. See `docs/results-and-limitations.md`.
